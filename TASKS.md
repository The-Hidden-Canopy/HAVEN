# Native Product Consolidation — Next-Phase Engineering Plan

Source: `HAVEN_Next_Phase_Engineering_Plan.docx`, repository review at `main @ 8a25904a`. This is a whole-repo strategic review, not a single-feature spec — its own thesis: the codebase has crossed from "WebUI product with an incomplete native facade" to "credible native product skeleton," so the next constraint is **coherence, not more screens**. Primary decision the plan asks to lock in: stop treating native parity as the roadmap; move the definition of done to end-to-end native workflows, real transports/providers, cross-domain orchestration, and recovery behavior. Priority order (why-now in the source doc's §Priority Map): **P0** native operational proof loop + discovery/connectivity breadth (code is ahead of hands-on validation; Wi-Fi discovery is SSDP-only, Bluetooth has an ABI but no Windows backend) → **P1** provider/credential foundation + cross-domain automation (comms can't be production-capable without real credentials; resource actions have no recurring-rule model the way home automations do) → **P2** relationship intelligence + tablet hardening.

Design principle from the doc (§2.3), worth keeping visible while working any of this: *"A feature should not be 'finished' when its page works. It is finished when the same object can participate in search, relationships, Today, tasks, permissions, automation, evidence and recovery without a domain-specific escape hatch."* The architectural risk named is fragmentation — each domain (Home, Computer, Communications, Tasks, Projects, Memory, Models) now has enough code to become its own app; the counter is a stronger shared layer (canonical resources, relationships, triggers, attention) so pages stay projections rather than becoming separate tools under one nav rail.

## Engineering decisions the plan asks to lock now (doc §16)

Not tasks — standing constraints to hold future work against: native is production, WebUI stays debug-only; discovery is never authoritative (seen/identified/provider-available/verified stay separate from "controllable"); one automation lifecycle spans every domain, never a second "agent automation" shortcut; credentials are a subsystem, not provider-config fields; pages are projections over canonical resources/relationships, not independent apps; interactive QA is part of definition of done now (integration defects, not missing methods, are the live risk); tablet is adaptive layout, never a second product; model proposals never become execution authority directly.
